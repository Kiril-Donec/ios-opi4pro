# Orange Pi 4 Pro — аппаратная проверка A733 XNU v17

**Статус на 21 октября 2026: v17 УСПЕШНО ПРОШЛА АППАРАТНЫЙ ТЕСТ на Orange Pi 4 Pro.** При запуске экспериментального XNU завершились `copyinstr()`, обе операции `open()` и многократные `write()` из тестового PID 1. Это **не полноценная iOS**: RAM-root содержит наш собственный тестовый Mach-O `/sbin/launchd`, а не настоящий Apple launchd.

## Что уже доказано на плате

- U-Boot → A733 Stage0 → XNU загружается на **одном Cortex-A76**.
- HDMI показывает диагностический текст.
- HFS+ RAM-root монтируется; тестовый PID 1 стартует.
- `getpid()` возвращает `1`.
- В v16 первый `open("/sbin/launchd")` зависает в `_bcopyinstr()` при чтении `0x1000004e0`. Последние отмеченные этапы: `COPYINSTR_VALIDATE_DONE errno=0`, затем `COPYINSTR_ASM_ENTER`; `ASM_DONE` отсутствует.

## Что изменилось в v17

- Для Cortex-A76 включён `__ARM_PAN_AVAILABLE__`. `user_access_enable()` временно отключает PAN перед чтением пользовательской памяти; `user_access_disable()` возвращает его после копирования.
- `kprintf` убран из промежутка между этими двумя вызовами.
- XNU собирается с `-mcpu=cortex-a76`; дополнительные ядра не включаются.

**Итог теста:** изменения v17 вместе устранили наблюдавшееся зависание `open()`; по одному тесту нельзя доказать, какое из двух изменений (PAN или вынос логирования) было решающим. Остальные части iOS не проверены.

## Результат реального теста v17 (21 октября 2026)

Пользователь прислал 7 фотографий HDMI-вывода. На них достоверно читаются:

```text
A733 PID1 V16: COPYINSTR_VALIDATE_DONE errno=0
A733 PID1 V17: COPYINSTR_ACCESS_BEGIN
A733 PID1 V17: COPYINSTR_ACCESS_END errno=0 len=13
A733 PID1 V15: NAMEI_COPY_DONE errno=0
A733 PID1 V15: NAMEI_LOOKUP_DONE
A733 PID1 V15: VN_AUTH_VNOP_OPEN_DONE errno=0
A733 PID1 V15: OPENAT_OPEN1_DONE errno=0
A733 PID1: syscall exit 5 errno=0 result=0
A733 PID1: syscall exit 5 errno=0 result=1
A733 PID1: syscall exit 4 errno=0 result=23
A733 init: still alive
```

Первые два `open()` успешны (сначала `/sbin/launchd`, затем `/dev/console`); тестовая программа продолжает работать, пишет повторяющиеся сообщения. На снимках также виден `getpid()` с результатом 1. **Зависание v16 пройдено.** Фотографии сами по себе не доказывают стабильность после длительной нагрузки, готовность настоящего launchd или наличие полноценной графической системы. По экрану нельзя установить SHA-256 именно записанного тестового IMG — не следует приписывать фотографиям какой-либо конкретный хэш из истории сборок.

## Если понадобится повторить тест или исследовать следующий сбой

**Дальнейшие фотографии того же стабильного цикла `A733 init: still alive` не нужны.** Этот этап успешно завершён. Если появится новый симптом, достаточно одного снимка последнего экрана и описания последовательности действий.

### Историческая таблица контрольных точек v17

Сфотографируй **последний экран**, захватив все сообщения начиная с `A733 PID1 V17` (если они появились). Пять минут ожидания не обязательны: для остановки в одном месте достаточно снимка спустя примерно минуту, но при активном изменении текста дай ему дописать.

| Последняя строка / результат | Что означает |
| --- | --- |
| `COPYINSTR_ACCESS_BEGIN`, затем `COPYINSTR_ACCESS_END errno=0` | Копирование пользовательской строки завершилось; проверяем далее `NAMEI_COPY_DONE`, lookup и завершение `open()`. |
| `COPYINSTR_ACCESS_BEGIN`, но `ACCESS_END` нет | Зависание осталось в доступе к памяти или исключении; нужны `ESR_EL1`, `FAR_EL1`, `ELR_EL1`, `TTBR0_EL1`, `TCR_EL1` и состояние PAN по доступным трассам. |
| PAN assertion / panic до `ACCESS_BEGIN` | Проверяем, что PAN устанавливается при входе в ядро и на переходах EL0 → EL1. |
| `NAMEI_COPY_DONE` и `OPENAT_OPEN1_DONE` | Изоляция предыдущей ошибки пройдена; анализируем возвращённый errno и дальнейший код PID 1. |
| Чёрный экран / ранняя ошибка Stage0 | Нельзя делать вывод о `copyinstr`; сначала проверяем хэш, версию IMG и цепочку загрузки. |

Не требуется снимать десятки почти одинаковых кадров: **один полный снимок последнего экрана** и, если есть, ещё один экран с ошибкой/исключением.

## Ранний разовый RAM-тест без записи поверх рабочего загрузчика (исторический способ)

Следующий путь применим **только при проверенном доступе к U-Boot и известной разметке**. В первом ext4-разделе `mmc 0:1` должны уже находиться `/ios-a733/stage0.uimg`, `/ios-a733/a733-xnu.payload` и `/ios-a733/a733-xnu-one-shot.scr`, а штатный DTB — по `/dtb/allwinner/sun60i-a733-orangepi-4-pro.dtb`.

```text
mmc list
mmc dev 0
ext4load mmc 0:1 0x44000000 /ios-a733/a733-xnu-one-shot.scr
source 0x44000000
```

**Не запускай `source` при ошибке предшествующей загрузки и не угадывай номер MMC.** Этот способ — отдельно от уже подготовленного AutoBoot IMG. Для полной последовательности этапов и ограничений проекта см. [README](../README.md).
