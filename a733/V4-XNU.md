# A733 XNU loader experiment (v4, cross-built)

**Status (2026-10-19): PSCI CPU_ON of A76 MPIDR 0x600 was verified on the
physical Orange Pi (MMFR0=0x0000000000101122). A genuine upstream topaz XNU
Mach-O was downloaded from the successful GitHub Actions xnu run #50,
commit `184f5b1d`, with SHA-256 `a64a992e447009279d6aae9277d15237a40e42d4217e7113576a4386e21228ef`.
It packs and validates against this Stage0, but it is **NOT A733-adapted**.
No XNU entry execution has been demonstrated on the Orange Pi. There is
**no SD image ready for flashing**; the user has only one working card.**

The owner's v3 screen diagnostic **did boot on the physical Orange Pi 4 Pro**.
This update starts from that exact v3 source while preserving its SD image.
No known-good v3 flash image has been overwritten by v4 development.

## What v4 adds

- Optional `SWEETXNU` v1 payload loader, matching the format generated by
  `ios-topaz/tools/mkpayload.py`.
- Bounds checks for every Mach-O segment and the kernel's reserved 1-GiB
  high-memory slice, ADT, boot-args and entrypoint; refuses malformed payloads.
  Includes sanity checks for Apple Device Tree root counts before writing RAM.
- Live FDT verification that both high kernel RAM and the loaded payload
  lie inside described DRAM and do not overlap FDT memreserve entries or
  `/reserved-memory` carveouts. The vendor's static DTB advertises only
  512 MiB; Linux's live FDT advertises 4 GiB, so the U-Boot handoff must
  provide the corrected live map or Stage0 will refuse the copy.
- Checks for EL1 with physical addressing safe (MMU and D-cache off), and
  cache-cleans the payload to PoC before the PSCI target CPU reads it.
- Bounded extraction of explicit `/chosen/a733,xnu-payload-start` and `-end`
  from the U-Boot-passed FDT. **Normal v3 boots remain display-only** without
  these fields; incidental U-Boot `linux,initrd-*` properties are ignored.
- PSCI `CPU_ON` of the first Cortex-A76 at MPIDR `0x600` if U-Boot began on
  an A55. The old CPU parks on success; the new CPU has its own stack.
- A separate **A76-only probe** without any XNU payload: U-Boot adds
  `/chosen/a733,a76-probe = <1>` and the second CPU displays its `MMFR0`.
- EL1/MMU/cache state and 16-KiB translation granule checks before jumping.
- Preliminary GICv3 A76 redistributor + Group-1 virtual timer PPI27 / SGI1
  setup using A733 addresses (not hardware tested); the distributor update
  enables Group 1 NS without inadvertently enabling Group 0.
- Early EL1 exception vectors showing fault slot, ESR, ELR and FAR on HDMI;
  XNU replaces those vectors when its kernel startup succeeds.
- iBoot-style XNU boot-args revision 2 and Apple Device Tree placement behind
  the loaded kernel, using the source project's `SWEETXNU` layout.
- Fail-closed manual boot script `tools/sd-boot-xnu-experimental.cmd` loading
  `stage0-v4.uimg` and `xnu.payload` without flash/partition writes.
- A lighter `tools/sd-boot-a76-probe.cmd` for the first hardware test. This
  proved the BL31/PSCI handoff and one physical A76 execution already.
- An **actual** topaz XNU Mach-O/payload was successfully parsed and tested
  through the same `xnu_validate()` function Stage0 uses. Sample physical
  entry `0x1014a6488`; a successful host-side check does not show XNU boot.
- A source patch `xnu-a733-firstboot.patch` produced directly from the
  xnu-buildtree of successful upstream CI run #50; `git apply --check`
  succeeds against that exact source.
- A fail-closed compiled-kernel audit `tools/audit_a733_macho.py` inspects
  XNU's actual `start_first_cpu` machine code (HDMI marker and stride),
  and compiled CPU/IOKit identity strings. It correctly **rejects** the
  original topaz CI kernel before any A733 image is created.
- The A733 ADT deliberately **does not expose Qualcomm display/watchdog
  devices**. Its early framebuffer console is direct to existing HDMI RAM,
  while the Qualcomm AppleCLCD / MDP driver must stay disabled.

## Still required before claiming XNU boots

1. **Rebuild an XNU-8796 Mach-O for A733 on macOS-14 CI.** The downloaded, working Xiaomi topaz/sweet binaries
   contain Qualcomm-specific CPU/interrupt/storage logic. In particular,
   topaz's SweetCPU expects MPIDR `0x100` and Kryo CPU device properties;
   A733 needs MPIDR `0x600` and Cortex-A76 matching. The A733 CPU driver,
   GIC timer integration, and early framebuffer driver must be built/tested.
   A read-only check and guarded adaptation of an **already
   ios-topaz-patched XNU source tree** is supplied:

   ```sh
   python3 tools/adapt_xnu_a733.py /path/to/patched-xnu --check
   python3 tools/adapt_xnu_a733.py /path/to/patched-xnu --apply
   # Or emit a reproducible git patch for the CI build:
   python3 tools/adapt_xnu_a733.py /path/to/patched-xnu \
     --emit-patch xnu-a733-firstboot.patch
   ```

   The adapter preserves `.pre-a733` backups and updates five XNU files:
   CPU identity, matching, the physical early console, and the bootstrap
   identity/final framebuffer block aliases. It is **not a complete A733
   XNU patch set**. All edits require one exact source match each, so
   divergent patch revisions fail without modifying the tree.

   **Critical A733 framebuffer detail:** `0xBBF11000` is only `0xEF000`
   bytes below the `0xBC000000` 32-MiB block boundary. The original Xiaomi
   XNU early console maps just one 32-MiB block at `0x9C000000`. Using the
   full 1024x600 A733 framebuffer with that mapping could touch an unmapped
   block before `arm_vm_init` finishes. The adapter maps the **aligned**
   A733 block `0xBA000000` and relocates its VA by `0x1F11000`. To stay
   strictly inside the block it draws early XNU diagnostic text only in
   the **top 224 native scanlines** (1024x224, BGRA 32bpp, stride 4096).
   This is a deliberate boot diagnostic crop, **not** the final display mode;
   the stage0 portrait screen remains 600x1024 logical. Full-height XNU
   framebuffer handling still requires porting the display driver.
2. **Physically validate high RAM `0x100000000..0x13fffffff` is free**, and
   PSCI `CPU_ON` plus timer/GIC behavior under the v59 U-Boot/BL31 version.
   A Linux FDT memory entry is not by itself sufficient to prove no live
   bootloader allocation survives there.
3. **Cross-compilation of stage0 v4 is done.** `make all` linked the AArch64
   ELF and generated a vendor-compatible uImage; `make test-boot` passed five
   tests including checking `a76_secondary_entry` and the second CPU stack.
   This establishes syntactic/linker and image correctness, not execution on
   the physical Cortex-A76.
4. The owner has **no spare microSD**. The only working card must not be
   overwritten just to reproduce a Stage0-only result. The next candidate
   board test needs a **new CI-built A733 XNU Mach-O** and a reversible boot
   plan; new MMIO access and kernel handoff can still hang/reset the board.
5. The experimental Apple Device Tree is minimal and has no A733 MMC root,
   touch, Wi-Fi, GPU, or iOS userland. A first XNU exception/panic is the
   realistic next milestone, **not** an iOS lock screen yet.

## Build and packaging outline

On Debian/WSL with AArch64 cross tools installed:

```sh
make test
make adt
make
# New result, if cross-build succeeds: build/stage0.uimg
```

With the existing, **unadapted** topaz kernel present at
`build/kernel.development.sweet`:

```sh
# This Xiaomi kernel is NOT safe for Orange Pi and is now rejected by
# the A733-specific packer and Stage0 payload magic:
make test-real-xnu   # Must FAIL for the unadapted Xiaomi kernel.
make test-hardware-fdt
make check-a733-xnu # Must FAIL for the unadapted Xiaomi kernel.
```

From a *separately compiled A733-adapted* XNU Mach-O (placeholder path):

```sh
python3 tools/package_xnu_a733.py \
  path/to/audited/kernel.development.sweet build/a733-early.adt build/a733-xnu.payload \
  --cmdline 'debug=0xc cpus=1 keepsyms=1 -v modem=0 wifi=0'
make test-real-xnu XNU_MACHO=path/to/audited/kernel.development.sweet
```

An A733-adapted Mach-O was compiled and passed a static marker audit in
GitHub Actions on 2026-10-19 (run 39293623008). Its physical execution on
Orange Pi has **not** been tested. This repository now requires the A733XNU1
payload tag, emitted only by the audited wrapper. The A76-only probe already worked on the real board and need not be
repeated. Do **not** flash or boot `build/a733-real-xnu-unadapted.payload`;
its original Xiaomi startup writes to 0x9C000000 and its drivers still target
Qualcomm peripherals.
Never rename the old v3 ELF/uImage to `stage0-v4.uimg` as a substitute. `bootm` loads the
new stage0 from the spare SD's `/ios-a733/stage0-v4.uimg`, and it expects the
payload at `/ios-a733/xnu.payload`; the script puts it in RAM at
  `0x52000000`, records its exact length in the A733-specific FDT properties,
  and passes control via
`bootm 0x42000000 - 0x43000000`. This U-Boot script syntax must be verified
on the actual board before deploying it as autostart.

Do not install this script as the default boot script yet. The v3 screen
diagnostic is the rollback path.

**Next test:** wait for a freshly built **A733-specific** kernel and package it
with the minimal ADT; take a copy of the single working microSD first. The
first useful observation is the XNU entry-stage white marker / early text,
or an exception, not an iOS home screen.
